# Lesson 17 — OpenAPI, CORS, filters & interceptors

> **Why this lesson exists:** Three practical concerns that make an API usable by other people. CORS in particular is the single most common "why doesn't my frontend work" problem in web development, and most developers "fix" it by copy-pasting a config that silently disables a security control. You'll understand it properly.

**Time:** ~60 minutes · **Prereq:** Lessons 14–16

---

## 1. The idea in one sentence

> **CORS is enforced by the *browser*, not your server: the request was sent, the server answered, and the browser refused to hand the response to JavaScript — and almost every confusion about it dissolves once you've seen that 200 in the Network tab.**

The other two topics are the same concern from different angles: documentation generated from your code can't drift away from it, and cross-cutting work only behaves if you put it at a layer that can actually see the requests it needs to.

## 2. OpenAPI / Swagger

**OpenAPI** is the specification (a JSON/YAML description of your API). **Swagger** is the tooling family that reads it (Swagger UI, Codegen). Historically the spec *was* called Swagger; it was donated to the Linux Foundation in 2015 and renamed OpenAPI. Using the terms correctly is a small credibility marker.

```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.7.0</version>
</dependency>
```

That single dependency gives you:
- `/v3/api-docs` — the OpenAPI JSON, generated by inspecting your controllers
- `/swagger-ui.html` — interactive documentation you can make live calls from

> **Note:** `springfox` is the older, abandoned library (last release 3.0.0, 2020, never supported Boot 3). **`springdoc-openapi` is the current one.** Recommending springfox in an interview dates you badly.

### How it works, and why that matters

springdoc reflects over your `@RestController` methods and reads `@RequestMapping`, `@RequestBody`, `@PathVariable`, Bean Validation constraints, and DTO structure. **Documentation is generated from the code**, so it can't drift out of date the way a hand-written wiki does.

**Which is the argument for good types:** `ResponseEntity<?>` documents nothing. `ResponseEntity<MonitorResponse>` or a plain `MonitorResponse` documents itself. Your `@Min(30)` constraint appears as `minimum: 30` in the spec. **Writing precise DTOs and constraints buys you free documentation** — a nice thing to point out in a code review.

### Configuring it well

```java
@Configuration
public class OpenApiConfig {

    @Bean
    OpenAPI vigilOpenApi() {
        return new OpenAPI()
            .info(new Info()
                .title("Vigil API")
                .version("v1")
                .description("Uptime monitoring and incident management")
                .contact(new Contact().name("Vigil").url("https://github.com/you/vigil"))
                .license(new License().name("Apache 2.0")))
            .servers(List.of(
                new Server().url("https://api.vigil.io").description("Production"),
                new Server().url("http://localhost:8080").description("Local")))
            .components(new Components()
                .addSecuritySchemes("bearerAuth", new SecurityScheme()
                    .type(SecurityScheme.Type.HTTP).scheme("bearer").bearerFormat("JWT"))
                .addSecuritySchemes("apiKey", new SecurityScheme()
                    .type(SecurityScheme.Type.APIKEY).in(In.HEADER).name("X-Api-Key")))
            .addSecurityItem(new SecurityRequirement().addList("bearerAuth"));
    }
}
```

The `securitySchemes` part matters: it puts an **Authorize** button in Swagger UI so you can paste a JWT and make authenticated calls. Without it, every protected endpoint returns 401 in the UI and people assume the docs are broken.

### Annotating for humans

```java
@Tag(name = "Monitors", description = "Create and manage uptime monitors")
@RestController
@RequestMapping("/api/v1/monitors")
public class MonitorController {

    @Operation(
        summary = "Create a monitor",
        description = "Creates a monitor that will be checked on the configured interval. "
                    + "The first check runs within one interval of creation.")
    @ApiResponses({
        @ApiResponse(responseCode = "201", description = "Created"),
        @ApiResponse(responseCode = "400", description = "Validation failed",
                     content = @Content(schema = @Schema(implementation = ProblemDetail.class))),
        @ApiResponse(responseCode = "402", description = "Monitor quota exceeded for plan",
                     content = @Content(schema = @Schema(implementation = ProblemDetail.class))),
        @ApiResponse(responseCode = "409", description = "Name already used in this organization")
    })
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public MonitorResponse create(@Valid @RequestBody CreateMonitorRequest request) { ... }
}
```

```java
public record CreateMonitorRequest(
        @Schema(description = "Human-readable name", example = "Production API")
        @NotBlank @Size(max = 100) String name,

        @Schema(description = "URL to check", example = "https://api.example.com/health")
        @NotBlank @SafeUrl String url,

        @Schema(description = "Seconds between checks", example = "60", minimum = "30")
        @Min(30) @Max(86400) int intervalSeconds
) {}
```

**`example` values are the highest-value annotation here.** Swagger UI pre-fills the "Try it out" body with them, so a new consumer can make a successful call in 10 seconds instead of guessing your schema. It's the difference between docs people use and docs people skim.

### Production hygiene

```yaml
springdoc:
  api-docs:
    enabled: true
    path: /v3/api-docs
  swagger-ui:
    path: /swagger-ui.html
    tags-sorter: alpha
    operations-sorter: method
    try-it-out-enabled: true
  packages-to-scan: com.vigil
  paths-to-exclude: /actuator/**, /internal/**
```

```yaml
# application-prod.yml
springdoc:
  api-docs:
    enabled: false          # or leave on but require auth
  swagger-ui:
    enabled: false
```

**Should Swagger UI be public in production?** For a *public* API (Stripe, GitHub, and Vigil-as-a-product), yes — it's marketing and onboarding. For an internal service, no: it's a free map of your attack surface, including parameter names and validation rules an attacker would otherwise have to guess. **The nuanced answer: expose docs for public APIs, protect or disable them for internal ones, and never expose an endpoint through Swagger that Spring Security doesn't also protect** — the docs aren't the security boundary.

**One more thing worth knowing:** commit the generated `api-docs` JSON and diff it in CI. A change to that file is a change to your API contract — reviewing it catches accidental breaking changes before clients do. That's a genuinely senior practice.

## 3. CORS — properly, not by copy-paste

### What problem CORS solves

Browsers enforce the **Same-Origin Policy**: JavaScript from `https://app.vigil.io` may not read a response from `https://api.vigil.io`. An *origin* is scheme + host + port — so `http://` vs `https://`, and `:3000` vs `:8080`, are different origins.

**Why the browser does this:** without it, any site you visited could issue authenticated requests to your bank (your cookies are attached automatically) and *read the responses*. Same-Origin Policy is what stops `evil.com` from reading your email.

**CORS (Cross-Origin Resource Sharing) is the server's way of saying "these specific other origins may read my responses."**

**Three things people get wrong, and they're worth being crisp about:**

1. **CORS is enforced by the browser, not the server.** `curl` and Postman ignore it entirely. So "CORS error" never means "my server rejected it" — the server usually responded fine and the *browser* refused to hand the response to your JavaScript.
2. **CORS does not protect your server.** It protects *users* from other websites. A malicious client can always call your API directly. **Authentication and authorization are your protection; CORS is not a security control for your API.** People conflate these constantly.
3. **The request often still happens.** For a "simple" request, the browser sends it, gets a response, and *then* discards it. So a cross-origin `POST` without preflight can still have written to your database.

### Preflight requests

For "non-simple" requests, the browser first sends an `OPTIONS` probe:

```http
OPTIONS /api/v1/monitors HTTP/1.1
Origin: https://app.vigil.io
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```
```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.vigil.io
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 3600
```

**"Simple" requests skip preflight**: GET/HEAD/POST with only CORS-safelisted headers and a `Content-Type` of `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`. **`application/json` is not on that list**, which is why virtually every JSON API request is preflighted. That's the reason `Access-Control-Max-Age` matters — without it, every request costs two round trips.

### Configuring CORS in Spring

**Global (recommended):**
```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://app.vigil.io", "http://localhost:3000")
                .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE")
                .allowedHeaders("Content-Type", "Authorization", "X-Idempotency-Key")
                .exposedHeaders("X-Correlation-Id", "X-RateLimit-Remaining")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

**Per-controller:**
```java
@CrossOrigin(origins = "https://app.vigil.io")
@RestController
public class MonitorController { }
```

**With Spring Security — and this is the part that trips everyone:**
```java
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .cors(Customizer.withDefaults())        // ★ REQUIRED, or the security filter chain
        .csrf(csrf -> csrf.disable())           //   rejects the OPTIONS preflight before
        .authorizeHttpRequests(a -> a           //   MVC's CORS handling ever runs
            .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
            .anyRequest().authenticated())
        .build();
}
```

**Why:** the security filter chain runs *before* `DispatcherServlet` (Lesson 14). An unauthenticated `OPTIONS` preflight carries no credentials, so Security rejects it with 401 — and the browser reports a CORS error. `.cors()` installs Spring Security's own `CorsFilter` early in the chain to handle preflights. **"CORS works until I add Spring Security" is one of the most common Spring questions on the internet, and this is the answer.**

### The security mistakes

```java
// ❌❌ The one that gets shipped constantly
.allowedOrigins("*").allowCredentials(true)
// This combination is ILLEGAL per spec, and Spring throws at startup —
// good, because it would mean "any website may make authenticated requests as your users."
```

```java
// ❌ Works, but disables the protection entirely
.allowedOriginPatterns("*").allowCredentials(true)
```
`allowedOriginPatterns` was added for legitimate wildcard subdomain cases (`https://*.vigil.io`), and people abuse it with `*` to silence errors. **With credentials allowed, `*` means any site can read your users' data using their cookies.** If you see this in a code review, it's a finding.

```java
// ✅ Legitimate patterns
.allowedOriginPatterns("https://*.vigil.io", "http://localhost:[*]")
```

**Environment-driven origins — what Vigil does:**
```yaml
vigil:
  cors:
    allowed-origins:
      - https://app.vigil.io
      - https://status.vigil.io
```
```yaml
# application-dev.yml
vigil:
  cors:
    allowed-origins: [ "http://localhost:3000", "http://localhost:5173" ]
```

Same code, different values — the Lesson 12 principle applied. No profile-conditional CORS logic.

## 4. Filters, interceptors, and aspects — the decision matrix

You met the mechanics in Lesson 14. Here's the decision table you should be able to reproduce, plus the implementations.

| Concern | Use | Why |
|---|---|---|
| Correlation ID / MDC | **Filter** | Must cover 404s, static resources, and errors |
| Request/response logging | **Filter** | Needs raw bytes; must log requests that never reach a handler |
| Authentication / authorization | **Filter** (Security's chain) | Must run before any handler; must short-circuit |
| CORS | **Filter** | Must answer OPTIONS before routing |
| Rate limiting | **Filter** | Cheapest possible rejection; must precede business logic |
| Response compression | Container config | Tomcat does it better than you will |
| Reading a custom annotation on the handler method | **Interceptor** | Needs the resolved `HandlerMethod` |
| Adding model attributes for views | **Interceptor** | MVC-aware |
| Per-endpoint audit with method args | **Aspect** | Needs typed arguments, not raw HTTP |
| Timing a service method | **Aspect** | Not an HTTP concern at all |
| Transactions, caching, retry | **Existing annotations** | Don't reinvent |

### A production request-logging filter

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
@Slf4j
public class RequestLoggingFilter extends OncePerRequestFilter {

    private static final Set<String> SKIP = Set.of("/actuator/health", "/favicon.ico");

    @Override
    protected boolean shouldNotFilter(HttpServletRequest req) {
        return SKIP.contains(req.getRequestURI());          // don't drown in health-check noise
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        long start = System.nanoTime();
        try {
            chain.doFilter(req, res);
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} {}{} -> {} ({}ms)",
                    req.getMethod(), req.getRequestURI(),
                    req.getQueryString() != null ? "?" + sanitize(req.getQueryString()) : "",
                    res.getStatus(), ms);
        }
    }

    private String sanitize(String query) {
        // ⚠️ Query strings contain tokens, API keys, emails. Redact before logging.
        return query.replaceAll("(?i)(token|key|password|secret)=[^&]*", "$1=***");
    }
}
```

**Three production details:**
1. **Skip health checks** — a Kubernetes liveness probe every 5 seconds is 17,000 useless log lines a day, per pod.
2. **Redact query strings** — API keys and tokens in URLs end up in logs, which end up in a log aggregator that more people can read than can read your database. This is a real and common leak.
3. **Don't log request bodies by default.** It requires `ContentCachingRequestWrapper` (buffering the whole body in memory — a DoS vector on large uploads) and bodies contain PII. Log bodies only for specific endpoints, behind a flag, with redaction.

### An interceptor that needs the handler method

```java
@Target(METHOD) @Retention(RUNTIME)
public @interface RequiresPlan { Plan value(); }
```
```java
@Component
@RequiredArgsConstructor
public class PlanGateInterceptor implements HandlerInterceptor {

    private final SubscriptionService subscriptions;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (!(handler instanceof HandlerMethod hm)) return true;

        RequiresPlan required = hm.getMethodAnnotation(RequiresPlan.class);   // ★ only possible here
        if (required == null) return true;

        if (!subscriptions.currentPlan().atLeast(required.value())) {
            res.setStatus(HttpStatus.PAYMENT_REQUIRED.value());
            return false;                                    // short-circuit
        }
        return true;
    }
}
```

**Why an interceptor and not a filter:** a filter has only the URL, so it would need a hand-maintained URL→plan map that drifts from the code. The interceptor reads the annotation off the *actual target method*, so the rule lives next to the endpoint it governs. **That's the whole reason interceptors exist**, and it's the answer to "when would you use an interceptor over a filter?"

Register it:
```java
@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {
    private final PlanGateInterceptor planGate;

    @Override public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(planGate).addPathPatterns("/api/**");
    }
}
```

### Filter ordering

```java
@Order(Ordered.HIGHEST_PRECEDENCE)      // correlation ID — must be first so everything logs it
@Order(Ordered.HIGHEST_PRECEDENCE + 10) // request logging
@Order(0)                                // rate limiting (cheap rejection, before auth work)
                                         // Spring Security's chain sits at -100 by default
```

Or register explicitly:
```java
@Bean
FilterRegistrationBean<CorrelationIdFilter> correlationIdFilter() {
    var reg = new FilterRegistrationBean<>(new CorrelationIdFilter());
    reg.setOrder(1);
    reg.addUrlPatterns("/*");
    return reg;
}
```

**A subtlety worth knowing:** `@Component` on a filter registers it for **all** URLs with no way to restrict patterns. `FilterRegistrationBean` gives you URL patterns and explicit ordering. Use `FilterRegistrationBean` when a filter shouldn't apply everywhere.

## 5. Rate limiting (a filter, and Vigil needs it)

Vigil's public status pages are unauthenticated and get hammered. Rate limiting is not optional.

```java
@Component
@Order(0)
@RequiredArgsConstructor
public class RateLimitFilter extends OncePerRequestFilter {

    private final RateLimiter rateLimiter;                  // Bucket4j / Redis-backed

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String key = resolveKey(req);                        // API key > user id > client IP
        RateLimitDecision d = rateLimiter.tryConsume(key);

        res.setHeader("X-RateLimit-Limit", String.valueOf(d.limit()));
        res.setHeader("X-RateLimit-Remaining", String.valueOf(d.remaining()));
        res.setHeader("X-RateLimit-Reset", String.valueOf(d.resetEpochSeconds()));

        if (!d.allowed()) {
            res.setStatus(429);
            res.setHeader("Retry-After", String.valueOf(d.retryAfterSeconds()));
            res.setContentType("application/problem+json");
            res.getWriter().write("""
                {"type":"https://vigil.io/problems/rate-limit","title":"Rate limit exceeded",\
                "status":429}""");
            return;                                          // short-circuit
        }
        chain.doFilter(req, res);
    }
}
```

**Design points that matter:**
- **Return the headers even on success.** Well-behaved clients self-throttle if you tell them their budget. Only telling them after they've failed is hostile design.
- **`Retry-After` on 429** is required for clients to back off correctly.
- **Key on identity, not just IP.** IP-only limiting punishes everyone behind a corporate NAT and is trivially bypassed with a proxy pool. Authenticated → user/org; unauthenticated → IP, and accept the imprecision.
- **In-memory counters don't work across instances.** Three pods with a 100/min in-memory limit means an effective 300/min. Use Redis (Bucket4j has a Redis backend) for a shared counter — or do it at the gateway/CDN, which is where it belongs at scale (Lesson 39).

Algorithms, briefly: **fixed window** (simple, but allows a 2× burst at the boundary), **sliding window** (accurate, more storage), **token bucket** (allows controlled bursts, the usual choice — and what Bucket4j implements), **leaky bucket** (smooths output). Token bucket is the right default and a good thing to name.

## 7. Production rules

| Do / Never | Why |
|---|---|
| **Use `springdoc-openapi`, never `springfox`** | Springfox's last release was 2020 and it never supported Boot 3; recommending it dates you immediately |
| **Declare precise return types, not `ResponseEntity<?>`** | The wildcard documents nothing, while a concrete DTO plus its validation constraints generates the schema for free |
| **Put `example` values on every DTO field** | Swagger UI pre-fills "Try it out" with them, so a new consumer succeeds in ten seconds instead of guessing your schema |
| **Disable or authenticate Swagger UI for internal APIs** | For a public API it's onboarding; for an internal one it's a free map of your attack surface, parameter names and validation rules included |
| **Never treat the docs as a security boundary** | Hiding an endpoint from Swagger does nothing; only Spring Security decides who may call it |
| **Diff the generated `api-docs` JSON in CI** | A change to that file *is* a change to your contract, and reviewing it catches breaking changes before your clients do |
| **Never combine `allowedOrigins("*")` with `allowCredentials(true)`** | Spring refuses this at startup on purpose — it would let any site on the internet make authenticated requests as your users |
| **List exact origins rather than patterns** | A pattern that accidentally matches `evil-vigil.io` is indistinguishable from a correct config until it isn't |
| **Set `maxAge` on your CORS config** | Otherwise every non-simple request pays an extra OPTIONS round trip, which on a chatty frontend doubles your request count |
| **Add `.cors(Customizer.withDefaults())` when Spring Security is present** | Otherwise the preflight is rejected with a 401 before your CORS config is ever consulted — the single most-asked Spring CORS question |
| **Put correlation IDs, request logging and auth in filters** | Only filters run for 404s, static resources and requests that never reach a handler, which is exactly when you want those |
| **Redact query strings and skip health checks before logging a request** | `?token=secret123` in a log aggregator is a credential leak, and health-check noise is what makes people stop reading logs |

## 8. Interview traps

**Q1. What is CORS and what problem does it solve?**
Browsers enforce the Same-Origin Policy so JavaScript on one origin can't read responses from another — which is what stops a malicious site from making authenticated requests to your bank and reading the result. CORS is the server opting specific other origins in, via `Access-Control-Allow-*` headers.

**Q2. Is CORS a security feature for your API?**
No — it protects *users* from other websites, not your server from clients. It's enforced by the browser; `curl`/Postman/mobile apps ignore it. Authentication and authorization protect your API.

**Q3. What is a preflight request and when does the browser send one?**
An `OPTIONS` probe asking whether the real request is permitted. Sent for "non-simple" requests — anything other than GET/HEAD/POST with safelisted headers and a form/text content type. `application/json` isn't safelisted, so nearly every JSON API call is preflighted. `Access-Control-Max-Age` caches the answer.

**Q4. Why does CORS break when you add Spring Security?**
The security filter chain runs before `DispatcherServlet`. The preflight `OPTIONS` request carries no credentials, so Security returns 401 and the browser reports a CORS failure. Fix: `.cors(Customizer.withDefaults())` so Security's `CorsFilter` handles preflights early (plus permitting `OPTIONS` if your rules require it).

**Q5. Why is `allowedOrigins("*")` with `allowCredentials(true)` illegal?**
It would mean any website may make credentialed requests as your logged-in users and read the responses — total defeat of the Same-Origin Policy. The spec forbids it and Spring throws at startup. Use explicit origins, or narrow `allowedOriginPatterns` like `https://*.vigil.io`.

**Q6. Filter vs interceptor — give a concrete example of each.**
Filter: correlation ID (must apply to 404s and static resources, which never reach a handler). Interceptor: a plan/feature gate reading a custom annotation off the target `HandlerMethod` — a filter only knows the URL and would need a hand-maintained map that drifts.

**Q7. Why extend `OncePerRequestFilter`?**
A plain `Filter` re-executes on internal `forward`/`include` dispatches, duplicating side effects. `OncePerRequestFilter` guards with a request attribute.

**Q8. How would you rate limit an API?**
A filter, keyed on API key or user ID (falling back to IP), with a token-bucket algorithm and a **shared** counter in Redis so it works across instances. Always return `X-RateLimit-*` headers on success and `Retry-After` on 429. At scale, push it to the gateway/CDN so bad traffic never reaches your app.

**Q9. Should Swagger UI be enabled in production?**
For a public API, yes — it's onboarding. For an internal service, disable it or require auth: it's a complete map of your attack surface, including parameter names and validation rules. Either way, docs are never the security boundary — Spring Security is.

**Q10. springdoc vs springfox?**
springdoc-openapi is current and supports Boot 3+. springfox is abandoned (last release 2020, no Boot 3 support). Recommending springfox dates you.

**Q11. What should never appear in request logs?**
Tokens, API keys, passwords, and PII — including in query strings, which are commonly logged verbatim. Redact before writing. And don't log request bodies by default: it requires buffering (a DoS vector) and bodies contain personal data.
